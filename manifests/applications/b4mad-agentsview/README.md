# b4mad-agentsview

[AgentsView](https://www.agentsview.io) session dashboard for the #B4mad
Network, at <https://agentsview.b4mad.industries>.

## What runs here, and what does not

AgentsView has two halves and only one of them is in this cluster.

- **`agentsview pg serve`** (this Deployment, `PG_SERVE=1`) is **read-only**.
  It renders a PostgreSQL database and nothing else: no local sync, no file
  watching, no session uploads.
- **`agentsview pg push`** runs on each *machine*, where the authoritative
  archive lives in `~/.agentsview/sessions.db`. Nothing in the cluster produces
  a session.

⚠️ Consequence worth stating plainly: with no machine pushing, this dashboard
is permanently empty and there is nothing wrong with it.

## Pushing from a machine

The database is exposed on a fixed NodePort on the node bridge — there is no
LoadBalancer/MetalLB on this single-node cluster (same constraint as Forgejo's
git-SSH). The gateway deliberately does **not** forward it: it is LAN-only.

```toml
# ~/.agentsview/config.toml
[pg]
url = "postgres://agentsview:${AGENTSVIEW_PG_PASSWORD}@192.168.0.148:32432/agentsview"
machine_name = "sisyphos"   # must be unique per machine, and never "local"
```

The password is generated by the CNPG operator:

```bash
oc -n b4mad-agentsview get secret prod-app \
  -o jsonpath='{.data.password}' | base64 -d
```

Then one-shot, or continuously:

```bash
agentsview pg push
agentsview pg push --watch      # or: agentsview pg service install
```

## Storage: deliberately unbacked

Unlike `b4mad-forgejo` and `b4mad-keycloak`, the CNPG cluster here has **no**
`barmanObjectStore` and no `ScheduledBackup`. Every row is derived from a
machine-local SQLite archive, so recovery is `agentsview pg push --full` on each
machine, not a restore. An S3 bucket, an `aws-creds` SealedSecret and a nightly
backup slot to protect a cache would be ceremony, not durability.

## Authentication

The Ingress reaches **oauth2-proxy** (`:4180`), never AgentsView. AgentsView
binds `127.0.0.1:8080`, so its only reachable path is through the sidecar in the
same pod.

- Realm **`erdgeschoss`**, not `b4mad-forgejo`. That realm brokers GitHub and
  Codeberg and auto-provisions accounts from them; with the client over there,
  the sole thing between any GitHub user and every prompt, tool result and
  `secret_findings` row in the archive would be an `--allowed-group` flag.
  `erdgeschoss` has no public identity provider, so it fails closed.
- The client is provisioned by `setup-agentsview-client-job.yaml` in
  `b4mad-keycloak` — realm `erdgeschoss` is create-only in git, so it follows
  the same PostSync-Job pattern as the Forgejo broker client.
- Any `erdgeschoss` user can sign in. To narrow that to a group, add an
  `oidc-group-membership-mapper` to the client and pass `--allowed-group` to
  oauth2-proxy.

### Rotating the client secret

One value in one place: `b4mad-keycloak/agentsview-oidc.enc.yaml`. Re-seal it,
and the PostSync Job pushes it to Keycloak while reflector mirrors it into
`b4mad-agentsview` for oauth2-proxy.

```bash
scripts/sops2sealedsecret --context <ctx> --namespace b4mad-keycloak \
  manifests/applications/b4mad-keycloak/agentsview-oidc.enc.yaml \
  manifests/applications/b4mad-keycloak/agentsview-oidc.yaml --force
```

## Two things that look wrong and are not

- **The pod reports `1/2` only while starting.** The `agentsview` container
  carries no probes: kubelet dials the pod IP, the process binds `127.0.0.1`,
  so no probe can reach it without giving up the loopback bind that makes
  oauth2-proxy the only way in. Readiness is oauth2-proxy's.
- **`could not write daemon runtime record: /data is not owned by current
  user`** on startup. `/data` is an emptyDir owned `root:<fsGroup>` and
  group-writable, and OpenShift runs the container as a random UID. The
  message only means the CLI cannot discover this daemon — irrelevant to
  `pg serve`, which reads PostgreSQL.
